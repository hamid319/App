## 7. The Hard Parts — Where to Put Most Effort

These are the technically complex, high-risk areas of the app. Mistakes here cause data corruption or bad UX.

### 🔴 HARDEST: Real-time Group Session Sync
**Why it's hard:**
- Multiple users swiping at the same time.
- Each swipe writes to Firestore transactions (`runTransaction`).
- `recordSwipeInSession` in `group_repository.dart` is 100+ lines of transaction logic.
- Race condition risk: two users voting on the same place at the same time → transaction must be atomic.
- `allMembersDone` check runs inside the transaction — if it fails (stale data), the session never auto-completes.
- The `streamSession()` provider keeps the UI reactive but adds complexity.

**What to watch:**
- Test with 3+ users swiping simultaneously.
- Verify the `isCompleted` transition only fires once, not twice.
- Check that the auto-redirect to `group-matches` fires on ALL devices, not just admin.

### 🔴 HARD: Router State + Auth State Coordination
**Why it's hard:**
- `GoRouter` refresh is tied to `userGroupsProvider.stream` but NOT `authControllerProvider.stream`.
- Logout does not trigger a redirect back to `/login` unless the stream changes.
- The `redirect` function runs async code (`PreferencesService.hasSeenOnboarding()`), which can cause timing issues.
- `_pickActiveSessionGroup` runs on every stream event — could trigger redirect loops.

**What to watch:**
- Test logout → confirm router goes to `/login`.
- Test fresh install → confirm onboarding shows.
- Test re-login → confirm onboarding does not show again.

### 🔴 HARD: Google Places API Integration
**Why it's hard:**
- Currently using 25 mock places (hardcoded Dart list).
- Real implementation requires: API key management, HTTP error handling, photo reference → image URL transformation, Firestore caching of results.
- Place IDs from Google Places API are long strings (e.g., `ChIJN1t_tDeuEmsRUsoyG83frY4`) — must replace mock integer IDs (`'1'`, `'2'`) everywhere.
- The `fetchExamplePlacesForLocation` method currently generates fake place IDs based on location + mock index — this breaks when switching to real API.
- Group sessions store place IDs in `placePool` — if IDs are inconsistent, the session breaks.

**What to watch:**
- The bridge between `fetchExamplePlacesForLocation` (used in sessions) and `loadNearbyPlaces` (used in solo swipe) must produce the same place IDs for the same places.
- Do not mix mock and real IDs.

### 🟡 MEDIUM-HARD: Favorites Consistency
**Why it's hard:**
- Favorites are stored as `List<String>` of place IDs in `users/{uid}.favorites`.
- `SwipeController` keeps an in-memory `_favorites` list that can drift from Firestore.
- `ProfileScreen` loads favorites with `FutureBuilder` (not reactive).
- If user removes a favorite in ProfileScreen, it calls `swipeControllerProvider.notifier.removeFavorite()` — but `swipeControllerProvider` may not be initialized if the user never went to the swipe tab.
- **Risk:** Removing favorite from profile crashes if swipe controller is in AsyncLoading state.

**What to watch:**
- Always guard `removeFavorite` with a null check on controller state.
- Consider moving favorites into a dedicated `FavoritesController` that both screens use.

### 🟡 MEDIUM-HARD: Swipe Controller State Lifecycle
**Why it's hard:**
- `SwipeController` builds once and is NOT rebuilt when group changes.
- If a user enters a session, swipes some places, ends the session, then starts a new session → the `_swipedPlaceIds` Set may contain stale data.
- `ref.invalidateSelf()` in `resetAll()` rebuilds the provider, but the router does not always call `resetAll()`.

**What to watch:**
- Verify that starting a new session reloads the swipe controller from scratch.
- Test the flow: Solo swipe → join group → start session → swipe → end session → start new session.

## 8. Firestore Data Structure (Actual)

```
/users/{uid}
  - uid: string
  - email: string
  - displayName: string?
  - photoUrl: string?
  - favorites: string[]      ← array of place IDs
  - groups: string[]
  - createdAt: timestamp

/places/{placeId}
  - id: string
  - name: string
  - description: string?
  - lat: double
  - lng: double
  - address: string?
  - imageUrls: string[]
  - averageRating: double?
  - types: string[]

/groups/{groupId}
  - groupId: string
  - groupName: string?
  - ownerUid: string
  - members: string[]        ← array of UIDs
  - sharedFavorites: string[]
  - location: {countryCode, countryName, cityId, cityName, lat, lng}
  - likeThreshold: int?
  - joinEnabled: bool
  - invite: {code: string, createdAt: timestamp}
  - activeSessionId: string?
  - hasCompletedSession: bool
  - createdAt: timestamp

  /sessions/{sessionId}
    - sessionId: string
    - destination: string
    - status: 'in_progress' | 'completed'
    - totalPlacesToSwipe: int
    - swipeLimit: int
    - placePool: string[]    ← array of place IDs
```
